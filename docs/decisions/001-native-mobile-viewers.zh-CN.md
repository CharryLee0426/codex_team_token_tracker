# ADR-001：原生移动查看器复用现有 Convex 查询

## 状态

已接受

## 日期

2026-09-04

## 背景

Codex Token Tracker 已有响应式 Next.js 仪表盘、Clerk 身份认证和带认证的 Convex 查询。本次
要求的 iOS 与 Android 应用只是查看入口，不是采集器：它们不能读取移动端文件、上传用量、控制
追踪设备，也不能展示桌面端安装流程。

移动端需要原生 SwiftUI 与 Kotlin/Compose 界面、实时个人/团队数据、安全会话、无需生产凭据的
确定性测试，同时尽量不增加新的后端与隐私边界。

## 决策

分别构建 SwiftUI 和 Jetpack Compose 查看器。应用使用 Clerk 官方原生 SDK 登录，并通过 Clerk
官方 Convex 桥接把认证交给 Convex 官方移动客户端，直接调用现有 `users:*`、`orgs:*` 和
`usage:*` 函数。

`users:ensureUser` 以及仅在当前组织尚未同步时使用的 `orgs:ensureCurrentOrg` 是唯一的应用启动
写操作；所有面向用户的移动功能保持只读。原生客户端从 Clerk（而不是 Convex 镜像）发现成员
关系，激活所选组织、等待 token 刷新，再通过 `orgs:byClerkId` 解析组织。团队授权必须同时满足
镜像 membership 与 Clerk 签名的当前 `org_id`，因此遗漏 membership webhook 不会留下无期限的
陈旧授权。

区间分块、紧凑行展开、仅 Codex 过滤和本地时区分组均为小型纯原生转换，由一份共享 fixture 和
双平台测试保护。

调试构建还支持明确标记的确定性演示模式。原生 UI 测试会强制使用此模式，因此端到端验证不依赖
外部 Clerk 状态、生产数据或网络。

## 已考虑的替代方案

### 用 WebView 包装响应式仪表盘

- 优点：代码最少，视觉和数据天然一致。
- 缺点：不满足原生 SwiftUI/Kotlin 要求，会重复浏览器导航，并且更难控制原生无障碍和离线状态。
- 结论：拒绝；所需产品是原生查看器，而不是打包网站。

### 新增移动 REST 读取 API 和自定义移动 token

- 优点：服务端统一返回形状，客户端聚合更少。
- 缺点：增加第二套认证/token 生命周期、新的外部隐私接口和部署耦合；已有原生 Convex 支持时并
  不值得。
- 结论：首版只读客户端不需要。

### 新增预聚合的 Convex 移动读模型

- 优点：减少重复转换和移动端载荷。
- 缺点：需要部署后端并设计带时区的服务端契约；在当前 UTC 不变量下，本地日期分组应位于查看端
  边界。
- 结论：暂缓；只有性能数据证明载荷或重复维护成本明显时再考虑。

## 影响

- 现有生产 schema 与 wire 协议保持不变。现有团队读取函数增加了更严格的当前组织授权检查；
  在实时原生团队访问可被视为安全之前，必须先部署该函数变更。
- 实时登录需要所有者启用 Clerk Native API、注册 bundle/package 标识，并在本机提供公开构建
  key；不会自动更改这一安全敏感的外部设置。
- Swift 与 Kotlin 需要镜像一小部分响应 schema，因为生成的 TypeScript 类型不能跨越原生边界；
  fixture 和解码测试用于防止漂移。
- 未签名的 CI/本地流程只能生成 iOS Simulator 应用，不能生成真机 IPA；商店分发属于后续签名与
  发布决策。
